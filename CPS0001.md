# CPS-0001 — Continuity Protocol Core

**v1.0-RC1** · Apache 2.0 · [The Continuity Lab](https://thecontinuitylab.org)

> A Continuity Protocol does not standardize how continuity is measured.
> It standardizes how continuity assertions are **represented, exchanged, and verified**.

## What Is This?

CPS-0001 defines the **Continuity Receipt** — a cryptographically verifiable statement that an observer collected sufficient evidence supporting the continuity of a subject over a bounded interval of time.

It is **engine-independent**. No sensor type, algorithm, or hardware requirement appears in the specification. A third party can build a completely different evidence engine — using different sensors, different algorithms, different hardware — and produce a valid Continuity Receipt that any conforming verifier can process.

## Why Does It Exist?

AI can now generate faces, voices, and behavior. "Who are you?" stops being the right question.

The right question: **who continues to be you?**

Continuity verification answers: is the subject at time t₁ the same subject observed at time t₀ — across the entire interval between them?

This is **not identity verification**. It doesn't answer "who is this?" It answers "is this the same subject as before?" The distinction is fundamental.

## Protocol at a Glance

```
ContinuityReceipt
├── Assertion   — what is claimed (3 closed assertions)
├── Evidence    — why it is believed (opaque engine payloads)
├── Context     — when / where / subject
├── Composability — predecessor reference (chain)
└── Signature   — who claims it
```

### What It Asserts

| # | Assertion |
|:---|:---|
| A₁ | **Observation Occurred** — real sensor data was collected |
| A₂ | **Continuity Maintained** — same subject at t₀ and t₁ |
| A₃ | **Receipt Integrity** — not modified since issuance |

### What It Does NOT Assert

Identity · Humanity · Liveness · Uniqueness (Sybil Resistance) · Location · Intent

### V₁–V₇ Verification Contract

| Step | Check | Engine-Dependent? |
|:---|:---|:---|
| V₁ | Schema validity | No |
| V₂ | Signature validity | No |
| V₃ | Assertion consistency | No |
| V₄ | Temporal consistency | No |
| V₅ | Evidence reference integrity | No |
| V₆ | Freshness | No |
| V₇ | Predecessor reference | No |

**None of the seven checks require knowing which evidence engine was used.**

### Normative Rules and Failure Codes (V₁–V₇)

This subsection is the **normative** definition of the verification contract: for
each check, the condition enforced, the failure condition, and the failure code a
conforming verifier MUST return. The failure-code vocabulary is closed for
v1.0-RC1 core conformance and is exactly the seven codes below.

#### Evaluation order and first-failure rule (normative)

The **normative evaluation order** of the core checks is:

```text
V₁ → V₂ → V₇ → V₃ → V₄ → V₅ → V₆
```

V₇ is evaluated **after V₂ and before V₃–V₆**. `previousReceiptHash` is unsigned
in v1.0 (see Annex N-1), so a receipt whose signature does not verify MUST NOT
have its chain pointer resolved; and a receipt-to-receipt continuity claim that
cannot be established is a more fundamental defect than a local assertion,
temporal, digest or freshness defect, so it is reported first.

**First-failure rule.** When more than one core check fails, the reported
`failureCode` **is the failure code of the first failing check in the normative
evaluation order above.** A conforming verifier MAY short-circuit at the first
failure, or MAY continue evaluating the remaining checks for diagnostics; but a
later failure MUST NOT displace, override, or replace the normative
first-failure code. The reported code is therefore a deterministic function of
the receipt and the supplied verification time, which is what makes conformance
reproducible for an independent implementation.

Within V₇, the four receipt-to-receipt checks are evaluated in the numbered order
1–4 of the table below, and the first of them that fails supplies the V₇ failure
code.

Throughout, `now` denotes the **verification time** supplied by the verifier. It
MUST be a caller-supplied value rather than an ambient clock read at an unspecified
moment, so that verification is reproducible. Conformance expected-results are
stated against the fixed evaluation time `2026-09-20T00:00:00Z`.

#### V₁ — Schema validity

| | |
|:---|:---|
| **Condition** | The receipt MUST conform to the normative JSON Schema (`continuity-protocol/schemas/continuity-receipt.schema.json`): all REQUIRED properties present, each present property of the declared type. `receiptId` is an opaque non-empty string; **no format constraint applies** (see Annex N-1 for its signed role). |
| **Failure condition** | Any REQUIRED property missing, or a property of the wrong type. |
| **Failure code** | `INVALID_SCHEMA` |

#### V₂ — Signature validity

| | |
|:---|:---|
| **Condition** | The Ed25519 signature MUST verify against `issuer.publicKey` over the canonical signing payload defined in **Annex N-1** (fixed 13-slot `":"`-joined string). `signature.algorithm` MUST be exactly `"Ed25519"`. |
| **Failure condition** | Signature does not verify; `signature.algorithm` is not `"Ed25519"`; or the key/signature bytes cannot be decoded per Annex N-1. |
| **Failure code** | `INVALID_SIGNATURE` |

#### V₃ — Assertion consistency

| | |
|:---|:---|
| **Condition** | The three assertions MUST be internally coherent. If `assertions.continuityMaintained.value` is `true`, then `assertions.observationOccurred.value` MUST also be `true` — claiming continuity without having observed anything is incoherent. |
| **Failure condition** | `continuityMaintained.value === true` while `observationOccurred.value === false`. |
| **Failure code** | `INCONSISTENT_ASSERTIONS` |

#### V₄ — Temporal consistency

All five conditions below are normative and MUST be enforced together. Any single
violation fails V₄ with `TEMPORAL_INCONSISTENCY`.

| # | Condition | Violation |
|:--|:---|:---|
| 1 | `interval.start < interval.end` | start is not strictly before end |
| 2 | `interval.end <= now` | the attested interval ends in the future and therefore was never observed |
| 3 | `coverageMs == interval.end - interval.start` | declared coverage does not equal the interval length |
| 4 | `signature.signedAt >= interval.end` | the receipt was signed before evidence collection completed |
| 5 | `expiresAt > interval.end` (when present) | expiry is not strictly after the interval it covers |

`now` MUST be supplied by the verifier (see above), which is what makes condition 2
testable. Every temporal input MUST be a parseable timestamp; an unparseable
`interval.start`, `interval.end`, `signature.signedAt`, or `expiresAt` fails V₄
rather than being silently ignored.

> **Reconciliation note (deliberate semantic decision).** Condition 5 binds
> `expiresAt` to `interval.end`, **not** to `signature.signedAt`. An earlier draft
> of the long-form presentation stated that `expiresAt` must be after
> `signature.signedAt`; that wording has no implementation or test support and is
> contradicted by the frozen normative vector `valid/agent-trace.json`, in which
> `expiresAt` precedes `signedAt` while remaining after `interval.end`. Expiry
> expresses the end of the window the receipt covers, so it is bound to that window.
> This is a semantic reconciliation, recorded so the rule is not mistaken for an
> accident.

| | |
|:---|:---|
| **Failure condition** | Any of conditions 1–5 violated. |
| **Failure code** | `TEMPORAL_INCONSISTENCY` |

#### V₅ — Evidence reference integrity

| | |
|:---|:---|
| **Condition** | For every `evidence[i]`, the recomputed `payloadDigest` MUST equal the declared `payloadDigest`, where the digest is `SHA-256(UTF-8(JSON.stringify(payload)))` using ECMAScript own-property enumeration order (integer-index keys ascending first, then other keys in insertion order; separators `,`/`:`; no whitespace; no Unicode normalization). This V₅ track is deliberately **not** JCS — see **Annex N-2**. The verifier MUST NOT inspect `payload` semantics. |
| **Failure condition** | Recomputed digest differs from the declared `payloadDigest` for any evidence block. |
| **Failure code** | `EVIDENCE_TAMPERED` |

#### V₆ — Freshness

| | |
|:---|:---|
| **Condition** | If `expiresAt` is present, `now < expiresAt`. An expired receipt remains cryptographically verifiable under V₁–V₅ and MUST NOT be accepted for live authorization, but expiry is not a signature failure. |
| **Failure condition** | `expiresAt` present and `now >= expiresAt`. |
| **Failure code** | `EXPIRED` |

#### V₇ — Predecessor reference (receipt-to-receipt, protocol core)

V₇ applies to a non-genesis receipt, i.e. one whose `previousReceiptHash` is not
`null`. A receipt with `previousReceiptHash === null` is a **genesis** receipt and
**skips V₇** — report `N/A`, not a failure. **`N/A` is permitted for no other
reason**: a non-genesis receipt is never `N/A`. The predecessor MUST be resolved
from a trusted store and never supplied by the presenter, because the pointer is
unsigned in v1.0 (see Annex N-1 and the trust-model note below).

**Predecessor resolution (normative).** For a non-genesis receipt, the
predecessor MUST be resolved from a trusted store. If `previousReceiptHash`
cannot be resolved to a predecessor receipt, then receipt-to-receipt continuity
is **not established**. V₇ therefore **fails**, the V₇ failure code is
`PREDECESSOR_MISSING`, and the overall result is `INVALID`. A verifier MUST NOT
report `N/A` for such a receipt, MUST NOT treat an unresolved pointer as an
absent one, and MUST NOT silently skip V₇ because no predecessor was available.

| # | Check | Failure code |
|:--|:---|:---|
| 1 | `SHA-256(JCS(predecessor)) === current.previousReceiptHash` | `CHAIN_BROKEN` |
| — | predecessor not found in trusted store | `PREDECESSOR_MISSING` |
| 2 | `current.subject.id === predecessor.subject.id` | `SUBJECT_MISMATCH` |
| 3 | `current.issuer.id === predecessor.issuer.id` | `ISSUER_MISMATCH` |
| 4 | `predecessor.interval.end <= current.interval.start` | `TEMPORAL_VIOLATION` |

`JCS` is RFC 8785 canonical serialization. `JSON.stringify(receipt)` is **not**
canonical and MUST NOT be used as the predecessor hash. V₇ runs **after** V₂
(signature) and **before** V₃–V₆.

These five codes are the **complete** v1.0-RC1 core V₇ conformance vocabulary.

### Revocation

CPS-0001 v1.0-RC1 does **not** define receipt revocation. There is no revocation
list format, no revocation status field, and no revocation failure code in this
version. Deployments that need revocation must implement it outside the protocol
core. This is stated explicitly so that no unsupported capability is inferred:
revocation is a future-extension candidate, not a v1.0-RC1 feature.

## Non-Goals

CPS-0001 does **not** define:

- **What an entity is.** The subject can be a human, an AI agent, a robot, or a device. CPS-0001 is entity-type-agnostic.
- **How evidence is collected.** Which sensors, algorithms, or hardware produced the evidence is outside the protocol's scope.
- **Whether a subject is alive, human, or unique.** Liveness, humanity verification, and Sybil resistance are separate concerns.
- **How a consumer should interpret evidence quality.** The protocol enforces structure. The consumer enforces policy.

CPS-0001 defines **how continuity evidence is represented and verified** — nothing more. It is a container for time-based trust, not a definition of what can be trusted.

## Protocol Architecture (Layered Design)

```
Layer 2: Application Profiles
  CPS-0001-H (Human) · CPS-0001-A (Agent) · CPS-0001-D (Device)
  Domain-specific schemas for Subject, Evidence, and Context blocks.

Layer 1: Domain Extensions
  AgentModelHash · DeviceState · FirmwareVersion · SessionContext
  Extensible fields that enrich continuity evidence per domain.

Layer 0: Core Protocol (CPS-0001)
  Receipt object model · V₁–V₇ verification contract · signature scheme
  Engine-independent, entity-type-agnostic. Designed to be stable for 10+ years.
```

Layer 0 is what CPS-0001 v1.0-RC1 defines today. Layers 1 and 2 are explicit extension points — reserved, not yet specified. They ensure the protocol can grow without breaking the core.

## V₇ — Predecessor Chain Verification (v1.0) — *see the normative section above*

> **This subsection is explanatory only.** The normative definition of V₇ — its
> conditions, its protocol-core failure codes, and the treatment of
> unresolved predecessors — is the **"V₇ — Predecessor reference (receipt-to-receipt,
> protocol core)"** subsection under *Normative Rules and Failure Codes (V₁–V₇)*
> above. That subsection governs; if anything here disagrees with it, that
> subsection wins.

V₇ binds a receipt to the immediate prior receipt in a continuity chain. A receipt
with `previousReceiptHash === null` is a **genesis** receipt and skips V₇.

**Receipt hash (canonical, protocol-level).** Each receipt is identified by:

```
receiptHash = SHA-256( JCS( receipt ) )
```

where `JCS` is RFC 8785 canonical serialization (recursive key sort, no
insignificant whitespace, `null` preserved, `undefined` rejected).
`JSON.stringify(receipt)` is **not** canonical and MUST NOT be used as the
predecessor hash.

**Verification (per non-genesis receipt).** Resolve the predecessor from a trusted
store by its `previousReceiptHash` (Model 3 — authoritative resolution), then apply
the protocol-core checks in the V₇ table above. A predecessor that cannot be
resolved from the trusted store fails V₇ with `PREDECESSOR_MISSING`.

### Annex N-1 — Normative Signing Input (frozen v1.0-RC1)

The normative Ed25519 input is the UTF-8 bytes of a 13-slot `:`-joined string. It
is NOT JCS, NOT
`JSON.stringify`, NOT lexicographic order, NOT "all fields":

```text
slot_separator = ":" (U+003A), no escaping, no quoting, no length-prefix.
slots = [receiptId, interval.start, interval.end, coverageMs(decimal, no leading zeros),
 subject.id, evidenceDigests(join ":"), issuer.id, issuer.publicKey,
 protocolVersion ?? "", expiresAt ?? "", assertionsFlat, verdict ?? "",
 references(join ":" in array order, empty -> "")]
assertionsFlat = [obs.value, obs.conf, cont.value, cont.conf, integ.value, integ.conf].join(":")
per-slot: string slot verbatim UTF-8 (no trim, no normalize);
 boolean true -> "true", false -> "false" (lowercase ASCII);
 coverageMs ECMAScript Number-to-String integer form;
 confidence finite double, ECMAScript Number::toString shortest round-trip form
 (e.g. 0.85 -> "0.85"); NaN/Infinity prohibited; no trailing zeros;
 missing/undefined optional slot -> "" (via ?? ""), never "null"/"undefined".
```

`:` occurs inside values (`sha256:…`, ISO `10:00:00.000Z`, digests). Verifiers MUST
reconstruct the fixed 13 slots field-by-field and MUST NOT `split(":")`-parse.
Unsigned in v1.0 (not in this payload): `previousReceiptHash`, `signedAt`,
`subject.type`, `evidence.engineId/version/confidence`, raw `payload`.
This annex freezes implementation behavior; any change (JCS-signing, escaping,
base64url, length-prefix) is a v1.1 breaking change and is OUT OF SCOPE.

**Key and signature encoding (v1.0, clarification of existing behavior — not a new
format or version).** Two fields are transported as byte strings, and their
canonical on-the-wire representation is **lowercase hexadecimal of the raw key
material**:

```text
issuer.publicKey  = raw Ed25519 public key, exactly 32 bytes,
                   lowercase hex, therefore 64 hex characters.
signature.value   = raw Ed25519 signature, exactly 64 bytes,
                   lowercase hex, therefore 128 hex characters.
```

These values are **NOT** base64url, **NOT** base64, **NOT** SPKI-DER, and **NOT**
PEM. The `signature.algorithm` string MUST be exactly `"Ed25519"`; `publicKey` is
the raw 32-byte key, *not* a DER-wrapped SubjectPublicKeyInfo, so verifiers MUST
decode the 64 hex characters directly rather than parsing an ASN.1 structure.
`signature.signedAt` is an ISO 8601 string and is unsigned, not hex-encoded.

This paragraph documents the representation already used by every conforming v1.0
implementation and by the frozen test vectors; it introduces no new version, no
new wire format, and no change to the 13-slot payload above.

### Annex N-2 — Digest Dual-Track (frozen v1.0-RC1)

V₅ track: `payloadDigest = SHA-256(UTF-8(JSON.stringify(payload)))`, where
`JSON.stringify` uses ECMAScript own-property enumeration order: integer-index
keys (canonical numeric strings 0..2³²-2) in ascending numeric order FIRST,
then other string keys in insertion order; separators `,`/`:` with no
whitespace; no Unicode normalization. Verified read-only: assigned
`b,10,2,a` serializes as `{"2":…,"10":…,"b":…,"a":…}` — insertion order does
NOT hold for integer-like keys. External implementations MUST emulate this
exact ordering, including integer-key reordering. This is a known v1.0
fragility, frozen, not fixed here.
V₇ track: `receiptHash = SHA-256(JCS(full receipt))` per RFC 8785 sort above.
The `JSON.stringify MUST NOT be used` prohibition above applies to the V₇
track ONLY and does not apply to the V₅ track.

**v1.0 trust model (important).** The `previousReceiptHash` pointer is **unsigned** in v1.0.
V₇ is secure *only* because the predecessor is resolved from a trusted store, not supplied
by the presenter. An attacker who controls the presented predecessor object cannot satisfy
the hash, because the store returns the genuine predecessor. Signed pointers (Design C) are
deferred to **v1.1**.

**Out of scope for pair-wise V₇:** fork detection (requires a single-successor registry) and
sequence-gap detection (requires the full chain or registry). Replay is covered by V₆ expiry
plus the Supabase replay registry.
