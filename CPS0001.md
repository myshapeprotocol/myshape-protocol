# CPS-0001 — Continuity Protocol Core

**v1.0-RC1** · Apache 2.0 · [The Continuity Lab](https://thecontinuitylab.org)

> A Continuity Protocol does not standardize how continuity is measured.
> It standardizes how continuity assertions are **represented, exchanged, and verified**.

---

## What Is This?

CPS-0001 defines the **Continuity Receipt** — a cryptographically verifiable statement that an observer collected sufficient evidence supporting the continuity of a subject over a bounded interval of time.

It is **engine-independent**. No sensor type, algorithm, or hardware requirement appears in the specification. A third party can build a completely different evidence engine — using different sensors, different algorithms, different hardware — and produce a valid Continuity Receipt that any conforming verifier can process.

## Why Does It Exist?

AI can now generate faces, voices, and behavior. "Who are you?" stops being the right question.

The right question: **who continues to be you?**

Continuity verification answers: is the subject at time t₁ the same subject observed at time t₀ — across the entire interval between them?

This is **not identity verification**. It doesn't answer "who is this?" It answers "is this the same subject as before?" The distinction is fundamental.

## Protocol at a Glance

```
ContinuityReceipt
├── Assertion   — what is claimed (3 closed assertions)
├── Evidence    — why it is believed (opaque engine payloads)
├── Context     — when / where / subject
├── Composability — predecessor reference (chain)
└── Signature   — who claims it
```

### What It Asserts

| # | Assertion |
|:---|:---|
| A₁ | **Observation Occurred** — real sensor data was collected |
| A₂ | **Continuity Maintained** — same subject at t₀ and t₁ |
| A₃ | **Receipt Integrity** — not modified since issuance |

### What It Does NOT Assert

Identity · Humanity · Liveness · Uniqueness (Sybil Resistance) · Location · Intent

### V₁–V₇ Verification Contract

| Step | Check | Engine-Dependent? |
|:---|:---|:---|
| V₁ | Schema validity | No |
| V₂ | Signature validity | No |
| V₃ | Assertion consistency | No |
| V₄ | Temporal consistency | No |
| V₅ | Evidence reference integrity | No |
| V₆ | Freshness | No |
| V₇ | Predecessor reference | No |

**None of the seven checks require knowing which evidence engine was used.**

## Non-Goals

CPS-0001 does **not** define:

- **What an entity is.** The subject can be a human, an AI agent, a robot, or a device. CPS-0001 is entity-type-agnostic.
- **How evidence is collected.** Which sensors, algorithms, or hardware produced the evidence is outside the protocol's scope.
- **Whether a subject is alive, human, or unique.** Liveness, humanity verification, and Sybil resistance are separate concerns.
- **How a consumer should interpret evidence quality.** The protocol enforces structure. The consumer enforces policy.

CPS-0001 defines **how continuity evidence is represented and verified** — nothing more. It is a container for time-based trust, not a definition of what can be trusted.

## Protocol Architecture (Layered Design)

```
Layer 2: Application Profiles
  CPS-0001-H (Human) · CPS-0001-A (Agent) · CPS-0001-D (Device)
  Domain-specific schemas for Subject, Evidence, and Context blocks.

Layer 1: Domain Extensions
  AgentModelHash · DeviceState · FirmwareVersion · SessionContext
  Extensible fields that enrich continuity evidence per domain.

Layer 0: Core Protocol (CPS-0001)
  Receipt object model · V₁–V₇ verification contract · signature scheme
  Engine-independent, entity-type-agnostic. Designed to be stable for 10+ years.
```

Layer 0 is what CPS-0001 v1.0-RC1 defines today. Layers 1 and 2 are explicit extension points — reserved, not yet specified. They ensure the protocol can grow without breaking the core.

## Protocol Success Criteria (§7.5)

A conforming implementation should answer **yes** to all three:

| # | Question | Test |
|:---|:---|:---|
| Q₁ | Can another team implement without using MyShape? | Give them only this spec. Can they produce a valid receipt? |
| Q₂ | Can two different engines produce interoperable receipts? | Run EE-001 and a third-party engine. Do both pass V₁–V₇ in the same verifier? |
| Q₃ | Can an app consume a receipt without knowing how evidence was generated? | Build an app that accepts a receipt and runs V₁–V₆ — without importing MyShape engine code. |

## V₇ — Predecessor Chain Verification (v1.0)

V₇ binds a receipt to the immediate, prior receipt in a continuity chain. A receipt with
`previousReceiptHash === null` is a **genesis** receipt and skips V₇.

**Receipt hash (canonical, protocol-level).** Each receipt is identified by:

```
receiptHash = SHA-256( JCS( receipt ) )
```

where `JCS` is RFC 8785 canonical serialization (recursive key sort, no insignificant
whitespace, `null` preserved, `undefined` rejected). `JSON.stringify(receipt)` is **not**
canonical and MUST NOT be used as the predecessor hash.

**Verification (per non-genesis receipt).** Resolve the predecessor from a TRUSTED store
by its `previousReceiptHash` (Model 3 — authoritative resolution). Then:

| Check | Failure code |
|:---|:---|
| `SHA-256(JCS(predecessor)) !== current.previousReceiptHash` | `CHAIN_BROKEN` |
| predecessor not found in trusted store | `PREDECESSOR_MISSING` |
| `current.subject.id !== predecessor.subject.id` | `SUBJECT_MISMATCH` |
| `current.issuer.id !== predecessor.issuer.id` | `ISSUER_MISMATCH` |
| `predecessor.interval.end > current.interval.start` | `TEMPORAL_VIOLATION` |

V₇ runs **after** V₂ (signature) and **before** V₃–V₆.

### Annex N-1 — Normative Signing Input (frozen v1.0-RC1, documentation of existing implementations)

The normative Ed25519 input is the UTF-8 bytes of a 13-slot `:`-joined string
(`src/lib/evidence/cps0001.ts:382-412`, mirrored byte-for-byte by
`continuity-protocol/cli/bin/cps-verify.mjs:57-82` and
`continuity-protocol/second-producer/noble-verifier.ts`). It is NOT JCS, NOT
`JSON.stringify`, NOT lexicographic order, NOT "all fields":

```text
slot_separator = ":" (U+003A), no escaping, no quoting, no length-prefix.
slots = [receiptId, interval.start, interval.end, coverageMs(decimal, no leading zeros),
 subject.id, evidenceDigests(join ":"), issuer.id, issuer.publicKey,
 protocolVersion ?? "", expiresAt ?? "", assertionsFlat, verdict ?? "",
 references(join ":" in array order, empty -> "")]
assertionsFlat = [obs.value, obs.conf, cont.value, cont.conf, integ.value, integ.conf].join(":")
per-slot: string slot verbatim UTF-8 (no trim, no normalize);
 boolean true -> "true", false -> "false" (lowercase ASCII);
 coverageMs ECMAScript Number-to-String integer form;
 confidence finite double, ECMAScript Number::toString shortest round-trip form
 (e.g. 0.85 -> "0.85"); NaN/Infinity prohibited; no trailing zeros;
 missing/undefined optional slot -> "" (via ?? ""), never "null"/"undefined".
```

`:` occurs inside values (`sha256:…`, ISO `10:00:00.000Z`, digests). Verifiers MUST
reconstruct the fixed 13 slots field-by-field and MUST NOT `split(":")`-parse.
Unsigned in v1.0 (not in this payload): `previousReceiptHash`, `signedAt`,
`subject.type`, `evidence.engineId/version/confidence`, raw `payload`.
This annex freezes implementation behavior; any change (JCS-signing, escaping,
base64url, length-prefix) is a v1.1 breaking change and is OUT OF SCOPE.

### Annex N-2 — Digest Dual-Track (frozen v1.0-RC1)

V₅ track: `payloadDigest = SHA-256(UTF-8(JSON.stringify(payload)))`, where
`JSON.stringify` uses ECMAScript own-property enumeration order: integer-index
keys (canonical numeric strings 0..2³²-2) in ascending numeric order FIRST,
then other string keys in insertion order; separators `,`/`:` with no
whitespace; no Unicode normalization. Verified read-only: assigned
`b,10,2,a` serializes as `{"2":…,"10":…,"b":…,"a":…}` — insertion order does
NOT hold for integer-like keys. External implementations MUST emulate this
exact ordering, including integer-key reordering. This is a known v1.0
fragility, frozen, not fixed here.
V₇ track: `receiptHash = SHA-256(JCS(full receipt))` per RFC 8785 sort above.
The `JSON.stringify MUST NOT be used` prohibition above applies to the V₇
track ONLY and does not apply to the V₅ track.

**v1.0 trust model (important).** The `previousReceiptHash` pointer is **unsigned** in v1.0.
V₇ is secure *only* because the predecessor is resolved from a trusted store, not supplied
by the presenter. An attacker who controls the presented predecessor object cannot satisfy
the hash, because the store returns the genuine predecessor. Signed pointers (Design C) are
deferred to **v1.1**.

**Out of scope for pair-wise V₇:** fork detection (requires a single-successor registry) and
sequence-gap detection (requires the full chain or registry). Replay is covered by V₆ expiry
plus the Supabase replay registry.
