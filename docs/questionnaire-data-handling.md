# Research Data Handling

Governance record for the public research instruments operated by The
Continuity Lab.

- `/lab/discovery-survey` → table `discovery_survey`
- `/lab/research-participation` → table `research_participation`

**One framework, two instruments.** Both follow the same consent, retention,
and withdrawal rules. There is no second governance system.

## The two instruments are different

| | Discovery Questionnaire | Research Participation |
|---|---|---|
| Route | `/lab/discovery-survey` | `/lab/research-participation` |
| Asks | whether a specific problem exists in your field | whether you want to take part in the research |
| Table | `discovery_survey` | `research_participation` |
| Consent version | `survey-consent-v1` | `participation-consent-v1` |
| Link between them | none | none |

Neither table references the other. A response to one is not a response to the
other, and the two are never joined.

## What Research Participation is not

Submitting the participation form is an expression of interest. It is not:

- product registration or an account,
- a participant ID or enrollment identifier,
- a Genesis 100 or recruitment application (see `recruitment_applications`),
- an EV-000 enrollment,
- a proof of humanity or any identity verification,
- a placement in any cohort.

No such mechanism is created by submitting the form, and none exists in the
code that handles it. It grants no status and no access.

## Consent

Consent is recorded, not assumed.

| Field | Meaning |
|---|---|
| `consent_at` | Server-generated timestamp of consent acceptance |
| `consent_version` | Identifier of the consent wording accepted |

Both tables use the same two fields with the same meaning.

- `consent_at` is generated by the server when the submission is accepted. A
  client cannot supply it — the API rejects any request that tries.
- `consent_version` must name wording the server supports. An unrecognised value
  is refused rather than stored.
- Consent wording is versioned per instrument. Changing the wording requires a
  new version for that instrument.

### Historical rows

Rows in `discovery_survey` submitted before the consent step existed have
`consent_at IS NULL` and `consent_version IS NULL`. This is intentional.

- `created_at` is **not** used as a consent timestamp.
- No default is applied, because a default would fabricate a consent record.
- A `NULL` consent means: *submitted before the consent step was introduced;
  whether consent was obtained at the time cannot be proven.*

`research_participation` is a new table, so it has no historical rows. The same
rule applies going forward: no backfill, no default.

### Known limitation

`discovery_survey` and `research_participation` both have an
`allow_anon_insert` policy with `WITH CHECK (true)`, which permits an
unconstrained direct insert. A caller holding the public anon key can
therefore write a row without going through the API, and such a row will have
no `consent_at`. Application-level consent enforcement is not a complete
guarantee until those policies are addressed. This is tracked separately as a
security issue and is deliberately out of scope for the governance work.

## Contact

`contact` is an **optional follow-up contact**, in both instruments.

- Optional, trimmed, length-capped, and stored as `NULL` when blank.
- It is used only to contact you about the research.
- It is not a participant ID, registration, enrollment, membership, or signup.
- Leaving it blank does not prevent your answers from being recorded.

`research_participation` additionally separates the intent from the value: a
`wants_contact` field records whether you asked to be contacted, and `contact`
is only accepted when that field is `yes`. The server rejects a payload that
sends a contact value without that intent, rather than silently discarding it.

## Retention

**Responses are retained for 180 days from submission, then deleted according to
the research data-handling policy.**

This 180-day window is a project governance decision for the current research
phase. It is a project policy — not a scientific standard, and not a legal
requirement. It applies to both instruments.

No automated deletion job is implemented. The policy and the audit fields are in
place; enforcing the window automatically is separate follow-up work.

## Withdrawal

There is no self-service deletion portal. Requests are handled manually by email.

Contact: **protocol@myshape.com**

Please state which of the two you mean — they are different requests:

### Stop future contact

We stop contacting you about the research. Your response is retained under the
retention policy above.

### Request deletion of an existing response

We locate the response and delete it. This cannot be undone.

### What to include

To help us locate the response, include whatever you have:

- the contact details you entered on the form, if you entered any;
- an approximate submission time;
- any answers you remember giving.

Contact details make a response easier to locate and verify, but they are not a
technical precondition for a deletion request. A request can still be made
without them.
