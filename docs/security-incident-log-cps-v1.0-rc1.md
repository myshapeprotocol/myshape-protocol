# CPS-0001 Security Incident Log

This document tracks all security-relevant changes and disclosures for CPS-0001.

## Incident: v1.0-RC1 Hardening Rollup

**Date**: 2026-08-25
**Status**: RESOLVED (no impact to frozen protocol semantics)
**Affected**: All implementations prior to v1.0-RC1

### Summary

Three security hardening issues were identified and remediated in the path to v1.0-RC1. None changed the core protocol semantics (V₁–V₇), but all addressed vectors that could undermine protocol integrity.

### Issues Addressed

#### 1. Private Key Storage in localStorage (Browser Engine)

- **Severity**: HIGH
- **Impact**: If an attacker achieved XSS on the MyShape web application, they could extract the Ed25519 private key directly from `localStorage['myshape_ed25519_secret']` as a hex-encoded string.
- **Root Cause**: Private key was stored as an extractable hex string in localStorage, readable by any JavaScript running on the page.
- **Fix**: Migrated to WebCrypto `CryptoKey` with `extractable=false`, persisted in IndexedDB. The signing key material is never exposed as a JavaScript string.
- **Scope**: Browser-side only (MyShape web implementation). Protocol specification unaffected.
- **CVE**: Not assigned — this was a client implementation issue, not a protocol vulnerability.

#### 2. Unsigned `coverageMs` in Signing Payload

- **Severity**: MEDIUM
- **Impact**: `interval.coverageMs` was serialized into the signing payload but the verifier did not enforce signature invalidation when this field changed. An attacker could alter `coverageMs` on an existing receipt without breaking the signature.
- **Exploitation**: Requires the attacker to obtain a valid receipt (trivial via their own key) but could be used to misrepresent temporal bounds to a trusting consumer.
- **Root Cause**: Field was present in payload digest for schema validation but not enforced as signature-covered content.
- **Fix**: Added `coverageMs` to `canonicalSigningPayload`. Any change now triggers `INVALID_SIGNATURE`.
- **Scope**: All implementations (3 producers/verifiers updated in lockstep).
- **Backwards Compatibility**: Receipts produced before this fix remain verifiable for their original `coverageMs`. New receipts are protected.

#### 3. Malformed Temporal Values Bypassing Freshness Checks

- **Severity**: MEDIUM
- **Impact**: Malformed timestamps (non-ISO strings, `NaN`-producing dates) could cause `freshness` checks to evaluate `NaN >= x` which is always `false`, effectively bypassing expiry.
- **Root Cause**: No explicit `isNaN()` / date validity guard in V₆ freshness check.
- **Fix**: Added `isNaN()` guards and explicit date parsing validation. Malformed values now return `TEMPORAL_INCONSISTENCY`.
- **Scope**: All implementations.

### Post-Hardening State

After v1.0-RC1, the following attack surface was eliminated:

| Attack Vector | Before | After |
|---|---|---|
| Private key extraction via XSS | ✅ High | ❌ None (non-extractable CryptoKey) |
| `coverageMs` tampering | ✅ Possible | ❌ INVALID_SIGNATURE |
| `expiresAt` NaN bypass | ✅ Possible | ❌ TEMPORAL_INCONSISTENCY |
| `signedAt` malformed bypass | ✅ Possible | ❌ TEMPORAL_INCONSISTENCY |
| Future interval injection | ✅ Possible | ❌ TEMPORAL_INCONSISTENCY |

### Acknowledgement

No external disclosure. This was identified during the internal forensics audit (Batch-2A through Batch-2E).

## Incident: Historical Key Storage Migration

**Date**: 2026-08-26
**Status**: DOCUMENTED (compatibility issue)

**Note**: Receipts generated by the v0.3.0 npm package (pre-Batch-2D) store identity using extractable hex keys. These receipts remain cryptographically valid, but the client-side key cannot be migrated to the non-extractable CryptoKey format without loss of the original key material.

**Mitigation**: Users transitioning from v0.3.0 should generate new identity keypairs. Old receipts remain verifiable for read-only validation purposes.
