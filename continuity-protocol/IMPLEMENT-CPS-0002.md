# CPS-0002 Implementation Guide (Prototype)

**Status**: PROTOTYPE — accompanies BATCH-0002-0.

---

## 1. What is CPS-0002?

CPS-0002 is an **additive** Human Signal Assertion layer. It does NOT replace
or modify CPS-0001. It references an existing CPS-0001 Continuity Receipt by
its canonical hash and produces a signed assertion about human presence.

```
CPS-0001 Receipt
   (SHA-256 over JCS canonicalization)
         ↓
    receiptHash
         ↓
CPS-0002 Assertion
   (12-field canonical payload, Ed25519 signed)
```

## 2. What problem does it solve?

CPS-0001 proves a keypair holder observed a subject continuously. Anyone with
an Ed25519 keypair can produce a valid CPS-0001 receipt — including a robot.

CPS-0002 asks: can we bind a receipt to a *human signal* in a way that is
composable with the existing engine-agnostic model?

## 3. What does the prototype actually prove?

The prototype proves **structural and cryptographic validity only**:

- The assertion conforms to the CPS-0002 schema (V0)
- The Ed25519 signature is valid for the 12-field canonical payload (V2)
- The referenced receipt hash matches the presented CPS-0001 receipt (V3)
- The assertion is within its validity window (V4)

It does **NOT** prove:
- Human authenticity, liveness, biological truth, absence of bots/Sybil

The `VALID` verdict means: "someone holding the stated attester key signed
this assertion." The relying application must make additional decisions.

## 4. How is a CPS-0001 receipt referenced?

```
reference.receiptHash = SHA-256( JCS( ContinuityReceipt ) )
```

This is the **exact same** `computeReceiptHash` function used by all CPS-0001
implementations. CPS-0002 reuses this — it does not define a new one.

## 5. How is the assertion signed?

1. Construct the 12-field canonical assertion payload (fields joined by `":"`)
2. Encode as UTF-8 bytes
3. Sign with Ed25519 using the attester's secret key
4. Store the signature in `signature.value`

The 12 signed fields:

| # | Field | Source |
|---|-------|--------|
| 1 | `protocolType` | `"cps-hsa-0.1-draft"` |
| 2 | `assertionId` | UUIDv7 (random or seed-derived) |
| 3 | `attester.id` | Derived from attester public key |
| 4 | `attester.publicKey` | Ed25519 public key (hex) |
| 5 | `subject.id` | From referenced CPS-0001 receipt |
| 6 | `reference.receiptHash` | `SHA-256(JCS(receipt))` |
| 7 | `reference.receiptId` | From referenced CPS-0001 receipt |
| 8 | `evidence.engineId` | Toy: `"TOY-HSA-999"` |
| 9 | `evidence.payloadDigest` | `SHA-256(UTF8(canonicalJSON(payload)))` — MyShape canonical JSON; **not** `JSON.stringify` |
| 10 | `validity.issuedAt` | ISO 8601 timestamp |
| 11 | `validity.expiresAt` | ISO 8601 timestamp |
| 12 | `signature.signedAt` | ISO 8601 timestamp |

## 6. How does verification work?

1. **V0 — Schema**: Validate JSON structure against schema
2. **V2 — Signature**: Reconstruct 12-field payload, verify Ed25519 signature
3. **V2.5 — Payload Digest**: Recompute
   `SHA-256(UTF8(canonicalJSON(evidence.payload)))` and compare with the signed
   `evidence.payloadDigest`. Mismatch → `INVALID_PAYLOAD_DIGEST`.
4. **V3 — Receipt Reference**: Verify `receiptId` and `subject.id` match the
   presented receipt (**first**), then recompute
   `SHA-256(UTF8(canonicalJSON(receipt)))` and compare with
   `reference.receiptHash`.
5. **V4 — Freshness**: Check `validity.expiresAt` hasn't passed.

> V1 is implicit in V2 — the verifier reconstructs the exact canonical payload.
> Step order is normative: see `CPS-0002-VERIFIER-CONTRACT.md` §4 (reference
> bindings precede the receipt-hash comparison, which determines the `reason`
> code on double-fault input).

`VALID` = all four checks pass. `VALID` ≠ proof of human.

## 7. How can an independent developer implement it?

1. Read this guide and `CPS-0002_CONCEPT.md`
2. Use the test vector at `test-vectors/cps0002/human-signal-01.json`
3. Reference the canonical payload field list above (Section 5)
4. Use any Ed25519 library (prototype uses `@noble/curves`)
5. Implement the canonical JSON rules in `CPS-0002-VERIFIER-CONTRACT.md` §5.0
   (MyShape canonical JSON). Any conformant RFC 8785 library also works for
   I-JSON-conformant input; note the compatibility boundary in §5.0 — the
   serialization does not reject non-finite numbers or lone surrogates. The
   prototype reuses `../shared/jcs`.
6. Run conformance tests:
   ```bash
   npx vitest run continuity-protocol/conformance/cps0002-conformance.test.ts
   ```

## 8. How do the test vectors work?

### human-signal-01.json

A deterministic vector generated by `scripts/gen-cps0002-test-vector.mjs`:

- References `test-vectors/valid/single-engine.json` (frozen CPS-0001 receipt)
- Uses fixed attester secret key
- Deterministic assertionId (seed-derived), timestamps, and evidence
- Reproducible by any implementation with the same inputs

### Deterministic parameters

| issuedAt | `2026-08-29T00:00:00.000Z` |
| expiresAt | `2026-08-29T01:00:00.000Z` |

| Evidence engineId | `TOY-HSA-999` |

## 9. What remains unresolved?

See `CPS-0002-THREAT-MODEL.md` for the complete list. Key unresolved topics:

- Trusted Issuer Registry (who is allowed to attest?)
- On-chain or off-chain attester key discovery
- Attester key revocation / rotation
- Cross-application replay prevention
- Production human-presence detection (NOT the toy evidence)
- Evidence quality scoring
- Identity graph binding
